# Brief Intake

[![CI/CD](https://github.com/SergeyLT/brief-intake/actions/workflows/ci.yml/badge.svg?branch=main)](https://github.com/SergeyLT/brief-intake/actions/workflows/ci.yml)

Первичный разбор заявок на интеграции и автоматизацию для менеджера команды разработки.

Сервис превращает свободный текст брифа в карточку для менеджера: извлекает задачу и системы, отмечает недостающие сведения, готовит вопросы и короткий черновик ответа. Карточка и исходник сохраняются в SQLite. Ответ заказчику проверяет и отправляет человек.

## Возможности

- `POST /ingest` принимает текст и возвращает сохранённую карточку; `GET /requests/{id}` показывает результат и аудит.
- Строгая JSON-схема, проверка цитат и обязательных сведений, эскалация при неопределённости, противоречиях и ошибках модели.
- Повтор с тем же `Idempotency-Key` возвращает прежний результат без нового вызова модели.
- Настраиваемые ограничения входа и числа вызовов, постоянный том SQLite, диагностические JSON-логи без содержимого заявок.

Готовность означает первичную техническую оценку специалистом. Сервис не оценивает стоимость и трудоёмкость, не обещает сроки и не подтверждает техническую реализуемость интеграции. Загрузка документов, подключение CRM и отправка писем не реализованы.

## Стек и устройство

| Задача | Технология |
|---|---|
| HTTP API и контракты | Python 3.12, FastAPI, Pydantic |
| Извлечение сведений | ProxyAPI, `openai/gpt-6-luna`, SDK `openai` |
| Карточки, аудит, квота и защита от повторов | SQLite, стандартный `sqlite3` |
| Проверки | pytest, Ruff, mypy |
| Запуск | Docker Compose |
| Поставка | GitHub Actions → GHCR → Coolify |

HTTP-слой проверяет доступ и вход, SQLite одной транзакцией закрепляет операцию и суточную квоту. Затем провайдер получает структурированный ответ модели. Бизнес-правила проверяют его, определяют статус и формируют короткое письмо из резюме и вопросов. Итог записывается до успешного ответа API. Во время сетевого запроса транзакция SQLite не удерживается.

Приложение рассчитано на один процесс и один worker с одной базой. Системная файловая блокировка запрещает одновременный запуск второго процесса на той же локальной БД. Сетевые файловые системы и несколько реплик не поддерживаются.

## Перед запуском

Нужны Docker с Compose v2, запущенный Docker Engine и ключ ProxyAPI с доступом к выбранной модели. На Windows используйте Docker Desktop в режиме Linux-контейнеров. Команды выполняются из корня скачанного репозитория.

Скопируйте `.env.example` в `.env`, укажите свой `PROXYAPI_API_KEY` и отдельный случайный `BRIEF_API_KEY`. Ключ приложения можно сгенерировать командой:

```sh
docker run --rm python:3.12-slim python -c 'import secrets; print(secrets.token_urlsafe(32))'
```

Вставьте результат в `BRIEF_API_KEY`. Значения-заглушки из примера приложение отклоняет. Не публикуйте `.env` и не используйте ключ ProxyAPI для доступа к приложению.

## Сборка и запуск на Windows

В PowerShell:

```powershell
Copy-Item .env.example .env
notepad .env
docker compose build
docker compose up -d
Invoke-RestMethod http://127.0.0.1:8000/health
```

Если `.env` уже настроен, первые две команды повторять не нужно. Отправка примера:

```powershell
$apiKey = Read-Host 'Введите BRIEF_API_KEY из .env'
$operationId = [guid]::NewGuid().ToString()
$headers = @{ 'X-API-Key' = $apiKey; 'Idempotency-Key' = $operationId }
$body = Get-Content -Raw -Encoding utf8 examples/brief.json
$card = Invoke-RestMethod -Uri http://127.0.0.1:8000/ingest -Method Post -Headers $headers -ContentType 'application/json; charset=utf-8' -Body ([Text.Encoding]::UTF8.GetBytes($body))
$card | ConvertTo-Json -Depth 12
Invoke-RestMethod -Uri "http://127.0.0.1:8000/requests/$($card.id)" -Headers @{ 'X-API-Key' = $apiKey } | ConvertTo-Json -Depth 12
docker compose exec -T api python -m brief_intake.audit
```

Повторите POST с теми же `$headers` и `$body`: ответ содержит ту же карточку, заголовок `Idempotency-Replayed: true`, новый вызов модели не выполняется. Для новой обработки создайте новый `$operationId` и обновите заголовок.

## Сборка и запуск на Linux

В Bash:

```bash
cp .env.example .env
${EDITOR:-vi} .env
docker compose build
docker compose up -d
curl -fsS http://127.0.0.1:8000/health
```

Если `.env` уже настроен, первые две команды пропустите. Отправка примера:

```bash
read -rsp 'Введите BRIEF_API_KEY из .env: ' BRIEF_KEY
printf '\n'
OPERATION_ID=$(cat /proc/sys/kernel/random/uuid)
mkdir -p output
curl -fsS http://127.0.0.1:8000/ingest \
  -H "X-API-Key: $BRIEF_KEY" \
  -H "Idempotency-Key: $OPERATION_ID" \
  -H 'Content-Type: application/json' \
  --data-binary @examples/brief.json \
  -o output/card.json
cat output/card.json
docker compose exec -T api python -m brief_intake.audit
```

Для чтения карточки подставьте её `id` вместо `<id>`:

```bash
curl -fsS "http://127.0.0.1:8000/requests/<id>" -H "X-API-Key: $BRIEF_KEY"
```

Повторите исходную команду POST с тем же `OPERATION_ID` для возврата прежнего результата. Новый идентификатор означает новую обработку. После работы удалите переменную с ключом: `unset BRIEF_KEY`.

## Вход и результат

Интерактивная документация доступна по `http://127.0.0.1:8000/docs`. Для POST в ней нужно указать общий ключ через Authorize и идентификатор операции в `Idempotency-Key`.

Вход — JSON с единственным полем `text`; пример находится в [examples/brief.json](examples/brief.json). Текст сохраняется без изменения. Пустой, пробельный и превышающий ограничение ввод отклоняется. Длинный текст не обрезается.

Карточка содержит `id`, даты, исходник `text`, `processing_state`, `result`, `error_code`, `error_type`, `model`, `usage`. В `result` находятся резюме, поля с `value` и дословным `evidence`, уверенность, причины эскалации, недостающие сведения, до пяти вопросов, черновик письма и следующий шаг.

| `result.status` | Значение |
|---|---|
| `ready_for_review` | Можно передать на первичную техническую оценку |
| `needs_clarification` | Нужно уточнить сведения или противоречия |
| `out_of_scope` | Явно вне специализации интеграций и автоматизации |
| `error` | Автоматический разбор не завершён, нужна ручная проверка |

Для первичной оценки нужны задача, источник и ожидаемое действие; для переноса данных — также целевая система. Отсутствие бюджета, срока или названия плагина само по себе не блокирует оценку. При низкой уверенности, неясной задаче или противоречиях эскалация обязательна. Поля, которых нет во входе, должны быть `null`. Упоминание «бюджет не определён» не является известным бюджетом. Цитаты проверяются по исходнику с нормализацией пробелов; эта проверка не доказывает правильность смысловой интерпретации.

HTTP 201 означает, что новая карточка сохранена, в том числе карточка с безопасным результатом `error` при сбое модели. Проверяйте бизнес-статус и `error_code`, а не только HTTP-код. Повтор готовой операции возвращает HTTP 200. Другой текст с прежним идентификатором — HTTP 409; сравнение текста точное, включая пробелы.

`processing_state` описывает техническое состояние: `processing`, `completed` или `interrupted`. Пока исходный запрос выполняется, повтор получает HTTP 409. Если процесс прервался после отправки провайдеру, исход внешнего вызова может быть неизвестен. При следующем старте такая операция помечается `interrupted`; повтор POST получает 409, а GET показывает безопасный результат и причину. Для намеренной новой попытки нужен новый идентификатор. Гарантии «ровно один внешний вызов при любом сбое» нет.

Неверный ключ даёт 401, неверный вход — 422, слишком большое HTTP-тело — 413, отсутствующая карточка — 404, исчерпанная квота — 429 с `Retry-After`, ошибка SQLite — 503. Исчерпание квоты не закрепляет новую операцию навсегда: после обновления квоты можно повторить её с тем же идентификатором.

## Конфигурация

Локально Compose читает `.env`. Переменные окружения процесса имеют приоритет. Python сам по себе `.env` не загружает.

| Переменная | По умолчанию / назначение |
|---|---|
| `BRIEF_API_KEY` | Обязательный общий ключ создания и чтения |
| `PROXYAPI_API_KEY` | Обязательный отдельный ключ провайдера |
| `PROXYAPI_BASE_URL` | `https://api.proxyapi.ru/v1` |
| `PROXYAPI_MODEL` | `openai/gpt-6-luna` |
| `PROXYAPI_TIMEOUT_SECONDS` | `45`, сетевой таймаут SDK |
| `PROXYAPI_MAX_COMPLETION_TOKENS` | `2000`, предел ответа модели |
| `PROXYAPI_TEMPERATURE` | `0.2`, при фиксированном `reasoning_effort=none` |
| `MAX_INPUT_CHARS` | `10000`, максимум символов входа |
| `DAILY_LLM_CALL_LIMIT` | `100`, общий суточный лимит новых вызовов |
| `HOST_PORT` | `8000`, локальный порт Compose |
| `APP_ENVIRONMENT` | `local`, окружение в логах |
| `APP_VERSION` | `0.1.0`, версия в health и логах |
| `DATABASE_PATH` | В контейнере `/data/briefs.sqlite3`; при Python-запуске `output/briefs.sqlite3` |

Квота считается за календарные сутки UTC и хранится в SQLite. Повторное чтение не расходует квоту. Зарезервированная попытка учитывается даже при ошибке или неизвестном исходе; автоматические повторы SDK отключены. Это ограничение числа вызовов, а не денежный бюджет аккаунта. Таймаут SDK не является строгим общим дедлайном всей обработки.

Модель выбирается через окружение, но совместимость другой модели со строгой схемой, `reasoning_effort=none` и температурой необходимо проверить отдельно.

## Данные и диагностика

SQLite находится в именованном томе `brief-data`. `docker compose down` сохраняет его, `docker compose down --volumes` удаляет карточки, аудит, квоту и историю защиты от повторов. Автоматического удаления данных нет. Владельцы общего ключа имеют одинаковый доступ ко всем карточкам; персональных прав и ролей нет.

Краткий аудит не выводит исходники и черновики:

```sh
docker compose exec -T api python -m brief_intake.audit --limit 10
docker compose logs --tail=100 api
```

Диагностические события приложения — JSON в stdout с `request_id` и внутренним `operation_id`. `X-Request-ID` возвращается клиенту. Исходники, ответы и ключи в эти события не включаются. Служебные сообщения Uvicorn имеют собственный текстовый формат. Docker ограничивает журнал тремя файлами по 10 МБ.

Локальный порт привязан к `127.0.0.1`. Для отдельной проверки задайте другой `HOST_PORT` и отдельное имя проекта: `docker compose -p brief-intake-check up -d --build`. У него будет собственный том. Не используйте имя рабочего проекта для тестовой очистки.

## Проверки

Виртуальное окружение размещается в `.venv`. На Windows:

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -e '.[dev]'
.\.venv\Scripts\python.exe -m ruff check .
.\.venv\Scripts\python.exe -m ruff format --check .
.\.venv\Scripts\python.exe -m mypy src
.\.venv\Scripts\python.exe -m pytest
```

На Linux — `python3.12 -m venv .venv`, затем те же команды через `.venv/bin/python`. Автотесты подменяют провайдера либо его HTTP-транспорт и не расходуют токены. Проверяются контракты, ошибки, обязательная эскалация, отсутствие утечек в логах, параллельные повторы, квота, перезапуск и запрет второго процесса.

Отдельный [набор из 10 заявок](evals/README.md) предназначен для живой проверки качества. Его запуск расходует токены и не входит в обычный pytest. Для фактической точности нужна также ручная проверка и новые независимые примеры.

## Развёртывание в Coolify

Контейнер запускается одним worker, использует постоянный том `/data` и endpoint `/health`. Ключи и ограничения передаются переменными окружения. Для внешнего доступа настройте HTTPS; создание и чтение карточек требуют ключа приложения.

[Workflow CI/CD](.github/workflows/ci.yml) выполняет проверки перед поставкой. На pull request к `main` он проверяет код и собирает Docker-образ без публикации. Push в `main` или ручной запуск на `main` публикует образ в `ghcr.io/<владелец>/<репозиторий>` с тегами `latest` и полного SHA. Имя образа автоматически приводится к нижнему регистру.

Сборка выполняется в Actions, Coolify скачивает готовый образ по [compose.coolify.yml](compose.coolify.yml). `compose.yml` остаётся локальной конфигурацией. В `/health` production-образа передаётся SHA коммита; workflow подтверждает совпадение ожидаемой версии после деплоя. Публикация и деплой из `main` выполняются последовательно. Обычные проверки и deploy health не вызывают модель.

Порядок первичной настройки:

1. Опубликуйте репозиторий с веткой `main`. Пока repository variable `DEPLOY_ENABLED` не равна `true`, workflow выполняет проверки и публикацию, а deploy пропускает. Проверьте первый успешный запуск и появление образа в GHCR.
2. Создайте в Coolify новое Docker Compose-приложение с доступом к репозиторию и файлом `/compose.coolify.yml`. Для приватного GHCR package настройте на сервере доступ Docker к реестру только на чтение пакетов. Доступ Coolify к Git-репозиторию сам по себе не является авторизацией в приватном GHCR.
3. Укажите в Coolify `GHCR_IMAGE` без тега и в нижнем регистре, `IMAGE_TAG=latest`, отдельные `BRIEF_API_KEY` и `PROXYAPI_API_KEY`. Остальные ограничения можно оставить по умолчанию. `APP_VERSION` в production не переопределяйте: она берётся из образа.
4. Подключите домен и HTTPS к сервису `api`, внутренний порт — `8000`. Постоянный том `/data` должен принадлежать этому ресурсу. Один экземпляр, один worker; не включайте параллельные копии на одном файле SQLite. Production Compose не публикует host-порты.
5. Отключите auto-deploy из Git и preview deployments для этого ресурса. Дополнительный GitHub repository webhook не нужен. Выполните первый ручной Deploy и проверьте `/health` и обработку примера.
6. В настройках ресурса Coolify → Webhooks скопируйте **Deploy Webhook (auth required)** вида `https://<coolify>/api/v1/deploy?uuid=<uuid>&force=false`. Manual Git Webhook не подходит. Подготовьте токен Coolify с правом Deploy.
7. В GitHub создайте Environment `production`. Задайте secrets `COOLIFY_WEBHOOK` и `COOLIFY_TOKEN` в этом окружении либо на уровне репозитория. Добавьте repository variables `PUBLIC_BASE_URL` — внешний HTTPS-адрес приложения **без `/health` и внутреннего `:8000`**, и `DEPLOY_ENABLED=true`. Ключи приложения и ProxyAPI в GitHub Actions не требуются.
8. Запустите workflow вручную на `main` либо сделайте новый push. Проверьте `checks`, `publish`, `deploy` и совпадение `/health.version` с SHA запуска. Успешный ответ webhook означает принятие запроса; только проверка health подтверждает нужную версию. При неопределённом исходе webhook не повторяется автоматически.

Для публикации используется встроенный `GITHUB_TOKEN` с `packages: write` только в job публикации. Токен чтения приватного GHCR хранится на deployment-сервере и не передаётся приложению. Workflow использует Environment `production`; ручное подтверждение требуется, только если вы отдельно настроили required reviewers.

## Резервное копирование и откат

Для согласованной копии работающей WAL-базы выполните в контейнере приложения:

```sh
python -m brief_intake.backup /data/backups/before-update.sqlite3
```

Путь назначения должен быть новым; существующая копия не перезаписывается. Перенесите файл из тома в отдельное защищённое хранилище. Копирование одного основного файла живой SQLite без Backup API может дать несогласованный результат.

Перед ручным откатом отключите автоматические деплои переменной GitHub `DEPLOY_ENABLED=false` и убедитесь, что уже запущенная поставка завершена. В Coolify задайте `IMAGE_TAG` полным SHA последнего исправного образа и выполните redeploy. Проверьте `/health`, чтение карточки и аудит. Верните `IMAGE_TAG=latest` перед возобновлением автоматических обновлений. При несовместимом изменении схемы потребуется восстановление согласованной копии при остановленном приложении; текущая версия не выполняет разрушительные миграции автоматически.

## Независимая проверка запуска

Для проверки воспроизводимости выполните инструкции Windows или Linux из свежего клона в отдельном каталоге; на сервере используйте отдельное имя Compose-проекта и свободный локальный порт. Проверьте сборку, обработку заявки, чтение и повтор, аудит и сохранность карточки после пересоздания контейнера без удаления тома. Рабочий экземпляр и его том должны оставаться независимыми от проверочного запуска.

[scripts/verify_api.py](scripts/verify_api.py) автоматически проверяет доступ, отклонение невалидного ввода, два реальных разбора (полный и неполный бриф), GET, повтор и конфликт идентификатора. Первичный запуск расходует два вызова модели. Ключ читается из `BRIEF_API_KEY` в окружении либо локального `.env`, не выводится и не сохраняется в результатах.

Для внешнего HTTPS API:

```sh
python scripts/verify_api.py --base-url https://your-domain.example --state output/api-verification.json
```

Замените адрес своим доменом. Повторная проверка сохранённых карточек после обновления не создаёт новых заявок:

```sh
python scripts/verify_api.py --base-url https://your-domain.example --state output/api-verification.json --check-existing --require-version-change --expected-version FULL_COMMIT_SHA
```

Укажите ожидаемый полный SHA вместо `FULL_COMMIT_SHA`. Для проверки после простого пересоздания той же версии опустите `--require-version-change` и `--expected-version`. Ошибка проверки даёт ненулевой код завершения; существующий файл результатов при первичном запуске не перезаписывается.

Если на Linux-хосте нет Python 3.12, используйте интерпретатор контейнера. Из корня клона в Bash:

```bash
docker compose exec -T api python - --base-url http://127.0.0.1:8000 --state /data/output/api-verification.json < scripts/verify_api.py
```

Здесь ключ берётся из окружения контейнера, а файл результатов сохраняется на постоянном томе. После `docker compose down` и `docker compose up -d --wait` выполните ту же команду с дополнительным `--check-existing` перед перенаправлением `< scripts/verify_api.py`.

- Адаптер формы сайта или CRM с сохранением идентификатора исходной заявки.
- Просмотр и утверждение карточек менеджером через интерфейс.
- Политика хранения и удаления под требования конкретного заказчика.
- Независимый набор обезличенных реальных брифов для оценки качества.
